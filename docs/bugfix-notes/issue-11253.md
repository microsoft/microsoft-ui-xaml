# Issue #11253: Application.UnhandledException doesn't catch async void exceptions if the app contains an Expander

https://github.com/microsoft/microsoft-ui-xaml/issues/11253

## Symptom

An app sets `e.Handled = true` in `Application.UnhandledException`, then throws from an
`async void` handler. Normally the app survives. But if the app has ever loaded an `Expander`,
the process fail-fasts instead.

## Root cause

Loading an `Expander` makes MUX run the class constructor for `ExpanderTemplateSettings`
(its template binds to `TemplateSettings`). `CClassInfo::RunClassConstructorIfNecessary`
(dxaml\xcp\core\metadata\ReflectionAPI.cpp:451-484) asks for an activation factory. For
`Microsoft.UI.Xaml.Controls.*` names, `ActivationFactoryCache::MuxGetActivationFactoryImpl`
(dxaml\xcp\core\dll\xcpcore.cpp:388) first probes MUXC through
`TryGetActivationFactoryFromModule(..., "DllTryGetActivationFactory")` (xcpcore.cpp:426).

MUXC has no factory for `ExpanderTemplateSettings`, so `DllTryGetActivationFactory` returns
`CLASS_E_CLASSNOTAVAILABLE` (controls\dev\dll\dllmain.cpp:328-345). That's expected; the
comment at dllmain.cpp:312-325 says so.

The bug: commit 7e63c33f5 ("Avoid calling RoOriginateLanguageException in MUXC when MUX is
trying to resolve a type") changed `TryGetActivationFactoryFromModule` from plain `return`s to
`IFC_RETURN`. `IFC_RETURN` records a MUX error context on the current thread (the UI thread).
Nothing clears it.

Later, the async void exception goes through `FinalUnhandledErrorDetectedRegistration::OnFinalUnhandledErrorDetected`
(dxaml\xcp\dxaml\lib\ErrorHelper.cpp:881), which calls `ProcessUnhandledError` with
`fSkipFailFastIfNoErrorContext = TRUE` (ErrorHelper.cpp:913). At ErrorHelper.cpp:572 it only
skips the fail-fast when `!HasCapturedErrorContexts()`. The stale context from the Expander
probe makes that false, so the process fail-fasts.

Confirmed earlier with a C# probe on shipping 2.5.1 bits (expander + unhandled crashes; plain,
or handled, survive) and cdb (the stale context is hr 0x80040111 from
`TryGetActivationFactoryFromModule`).

## Fix

dxaml\xcp\core\dll\xcpcore.cpp:325-339 (`TryGetActivationFactoryFromModule`):

| Before | After |
|--------|-------|
| `IFC_RETURN(CLASS_E_CLASSNOTAVAILABLE);` | `return CLASS_E_CLASSNOTAVAILABLE;` |
| `IFC_RETURN(pfn(activatableClassId, &activationFactory));` | `const HRESULT hr = pfn(...); if (FAILED(hr)) { return hr; }` |

Plus a comment saying why this must not use `IFC_RETURN`.

This is exactly the code from before 7e63c33f5 (see `git show 7e63c33f5 -- src/dxaml/xcp/core/dll/xcpcore.cpp`).

## Why this fixes it

- The only thing that put a context on the UI thread was `IFC_RETURN` in this function. With
  plain returns, a miss records nothing.
- Every caller treats a failure here as "try the next thing":
  - MUXC path: falls back to MUX's own `DllGetActivationFactory` (xcpcore.cpp:434-444), and
    that miss already uses `IFC_NOTRACE_RETURN` (dxaml\xcp\dxaml\dllsrv\winrt\dllentry.cpp:301).
  - dcompi / Microsoft.UI.Input / CoreMessagingXP paths (xcpcore.cpp:469, 484, 498): fall back
    to `RoGetActivationFactory` (xcpcore.cpp:507).
- Both brainstorm models traced the rest of the path (dllentry.cpp, ComPtr, ReflectionAPI) and
  found nothing else that records a context on this miss.
- The new test fails before the fix and passes after (below).

## Why it's safe

- It's a revert of two lines to what shipped before 7e63c33f5. The rest of that PR (the
  `DllTryGetActivationFactory` export and the `exportName` parameter) stays.
- 7e63c33f5's own stated goal is to "quietly return a failure code" for these probes
  (comment at xcpcore.cpp:422-425). `IFC_RETURN` went against that goal.
- Return values don't change. Callers see the same HRESULTs.
- The only lost behavior is the debug trace / error context for an expected miss. A real
  failure still surfaces through the fallback (`RoGetActivationFactory`), which reports its own
  error.

### Plain return vs. IFC_NOTRACE_RETURN

`IFC_NOTRACE_RETURN` (dxaml\xcp\components\base\inc\minerror.h:713) would also avoid the
context. I used plain returns because:
- That's what the code was before the regression.
- This function is a speculative probe; a miss isn't an error worth a verify_hresult either.

Either would fix the bug.

## Test

`StowedExceptionTests::ExpectedActivationFactoryMissLeavesNoErrorContext`
(dxaml\test\native\external\foundation\stowed\StowedExceptionTests.cpp:626-680):

1. Clear error contexts on the UI thread and check the TLS slot is null.
2. Put an `Expander` in the window, wait for idle, then expand it and wait for idle.
3. On the UI thread, check the error-context TLS slot is still null (StowedExceptionTests.cpp:677).

`IsolationLevel=Method` (StowedExceptionTests.h) because the class constructor only runs on the
first lookup per process. `Data:PerfOptIn={true}` to match how apps run.

Why not a C# test: C# test-app types are Custom kind, and
`RunClassConstructorIfNecessary` only calls `GetActivationFactory` for `TypeKind_Metadata` types,
so a C# test could pass without hitting this path.
