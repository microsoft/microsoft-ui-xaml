# Issue #12138: 1px gap at the top with FullScreen presenter and Window.ExtendsContentIntoTitleBar

## The bug

Set `Window.ExtendsContentIntoTitleBar = true`, then `AppWindow.SetPresenter(AppWindowPresenterKind.FullScreen)`.
The XAML content starts 1 physical pixel below the top of the screen. The top row shows the window background.

## Root cause

With `Window.ExtendsContentIntoTitleBar` on, WinUI leaves the top client row empty, so the native (DWM) top border can show there.

- `CWindowChrome::GetTopBorderHeight` returns 1 whenever Window ECITB is on and the window is not maximized (dxaml\xcp\components\WindowChrome\CWindowChrome.cpp:188, old comment said "fullscreen and borderless presenters are not checked").
- `UpdateBridgeWindowSizePosition` puts the XAML bridge HWND at `y = GetTopBorderHeight()` with height `clientHeight - GetTopBorderHeight()` (CWindowChrome.cpp:378, :398).

The FullScreen presenter removes all frame styles. There is no native border to show. But the 1px row was still reserved, so it showed up as a gap.

Measured on the Win11 VM (logged by `WindowTopBorderPainting`):

| State | GWL_STYLE | GWL_EXSTYLE | Frame bits |
|-------|-----------|-------------|------------|
| Overlapped (default) | 0x14cf0000 | 0x100 | WS_CAPTION (WS_BORDER + WS_DLGFRAME), WS_THICKFRAME |
| Overlapped, maximized | 0x15cf0000 | 0x100 | same |
| Overlapped, `SetBorderAndTitleBar(false, false)` | 0x144f0000 | 0x100 | WS_DLGFRAME, WS_THICKFRAME |
| CompactOverlay | 0x14c80000 | 0x108 | WS_CAPTION |
| FullScreen | 0x14000000 | 0x0 | none |
| Overlapped, app clears WS_OVERLAPPEDWINDOW (+ WS_POPUP) and sends SWP_FRAMECHANGED | 0x14800000 (0x94800000) | 0x0 | WS_BORDER is still set |

The last row is a one-off experiment. AppWindow (or Windows) keeps `WS_BORDER` on, so an app can't make an Overlapped window frameless by editing styles.

## The fix

- `GetTopBorderHeight` now also returns 0 when the top-level HWND has none of `WS_BORDER`, `WS_DLGFRAME`, `WS_THICKFRAME`, and no `WS_EX_DLGMODALFRAME` (CWindowChrome.cpp:198-203).
- `UpdateBridgeWindowSizePosition` used to skip the move when the bridge's client rect matched the new rect. That rect always has top 0, so a move from y=1 to y=0 with the same height would be skipped. It now also compares the bridge's real top in the parent (CWindowChrome.cpp:379-383, :399-402). This only adds `SetWindowPos` calls; it never removes one.

## Why this fixes it

- FullScreen has none of those bits, so the bridge goes to y=0 and gets the full client height.
- The bridge position is refreshed on `WM_SIZE` (DesktopWindowImpl.cpp:1961 -> `ResizeContainer` -> `UpdateContainerSize` -> `UpdateBridgeWindowSizePosition`).
- Entering FullScreen changes the style and then resizes the window to the monitor. So the `WM_SIZE` sees the new style. The test confirms this: offset is 0 right after `SetPresenter(FullScreen)`.
- Leaving FullScreen restores the frame styles and resizes again, so the offset returns to 1. The test checks this too.
- Toggling ECITB while in FullScreen doesn't send `WM_SIZE` (client size doesn't change). Before, this left the bridge stale (the old test comment said so). Now the offset is 0 for both ECITB values in FullScreen, so there's nothing to go stale.

I chose the style check over querying the presenter kind:

- `ShouldPaintTopRowOfClientArea` notes that HWND styles can change before AppWindow reports the new presenter (CWindowChrome.cpp:223). A presenter check during `WM_SIZE` could see the old presenter.
- A presenter check would also need an extra refresh on presenter change on Win11. Today that refresh is Win10-only (DesktopWindowImpl.cpp:1199-1205).
- `GetTopBorderHeight` is `const noexcept`. A style read can't fail in a way that needs handling.

## Why it's safe

- Only windows with Window ECITB on, not maximized, and with no frame style at all are affected. On Win11 that's only FullScreen in the table above. Overlapped and CompactOverlay keep their frame styles and still get 1 px (both measured).
- Borderless Overlapped (`SetBorderAndTitleBar(false, false)`, issue #9621) keeps `WS_DLGFRAME` and `WS_THICKFRAME`, so it is unchanged. That case is out of scope here.
- `WS_DLGFRAME` and `WS_EX_DLGMODALFRAME` are in the check to stay conservative: any window with a dialog frame keeps today's behavior.
- The offset change applies on all OSes, not just Win11. The Win10 top-row painting already skipped frameless windows, so on Win10 the only change is the same 1px offset fix.
- A frameless window has no native border, so XAML at y=0 can't cover one.
- `ShouldPaintTopRowOfClientArea` (Win10 top-row painting and DWM margins) already returned false for these windows. It returns false early when `GetTopBorderHeight()` is 0, so its result doesn't change. Its own style check (CWindowChrome.cpp:218-226) is still needed: a `WS_DLGFRAME`-only window gets offset 1 but no painting.
- `Window.Bounds` uses the top-level client rect, not the bridge, so it doesn't change (DesktopWindowImpl.cpp `get_BoundsImpl`).
- Drag/caption regions are computed from XAML element positions relative to the island, and are cached (`m_dragRegionCached`, CWindowChrome.cpp:437-457). With the island at y=0, island and client coordinates line up. I didn't test drag regions in FullScreen.
- Visible change for apps: in FullScreen with Window ECITB, content gets 1 more physical pixel of height and starts at the top of the screen. That's the requested behavior.

## Test

`WindowIntegrationTests::WindowTopBorderPainting` (dxaml\test\native\external\controls\window\WindowIntegrationTests.cpp):

- The FullScreen steps now expect offset 0 for both ECITB values, instead of `extendedOffset` (1 for the Window ECITB entry point).
- Removed the comment that said the bridge could stay stale in frameless transitions.
- Existing steps still check that leaving FullScreen goes back to offset 1, and that borderless Overlapped stays at 1.
- The state log line now includes GWL_STYLE and GWL_EXSTYLE, so failures show which frame bits were present.

## Review round 1 notes

- Reviewers asked for a refresh on style-only frame changes (`WM_STYLECHANGED` / `SWP_FRAMECHANGED`). I tried a `WM_WINDOWPOSCHANGED` hook with a test that strips the frame. The strip never produced a frameless Overlapped window: `WS_BORDER` stayed on, even with `WS_POPUP` (table above). So offset 1 stays correct, and the hook had nothing to fix. I removed it rather than ship untested code.
