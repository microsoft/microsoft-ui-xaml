Fix crash when tabbing to a Hyperlink in non-selectable text with caret browsing on (#10764)

## Bug

Issue #10764: with caret browsing on (F7), tabbing to a `Hyperlink` inside a `TextBlock` or `RichTextBlock` with `IsTextSelectionEnabled="False"` crashes the app with an access violation.

When a Hyperlink gets focus in caret browsing mode, `CHyperlink::FocusChangedEventListener` moves the caret to the Hyperlink. It asks the host for its selection, then reads the selection offsets.

| Host | Selection source |
|---|---|
| TextBlock | `CTextBlock::GetSelectionStart/End` |
| RichTextBlock | `CRichTextBlock::GetSelectionStart/End` |
| RichTextBlockOverflow | The master RichTextBlock (`m_pMaster`) |

`GetSelectionStart/End` return `S_OK` with a null pointer when text selection is disabled. The listener then calls `selectionStart->GetOffset(...)` on the null pointer.

Caret browsing also makes TextBlock and RichTextBlock tab stops (`FocusProperties.cpp`), so a user can reach the Hyperlink with Tab.

## Fix

In each of the three host branches in `FocusChangedEventListener` (`Hyperlink.cpp`), return early when the selection start or end is null.

- There is no caret to move when selection is disabled. `Select()` already does nothing in that case.
- Nothing else runs after this block in the function. Render invalidation has already happened.
- The RichTextBlockOverflow branch uses `IFCFAILFAST` on the `GetSelection*` calls. That only checks the HRESULT, so it didn't catch the null.

In the TextBlock branch, the listener also calls `GetSelectionManager()` first.

- TextBlock creates its selection manager lazily. `GetSelectionStart/End` don't create it, so they return null until it exists, even when selection is enabled.
- Without this call, the new early return would skip moving the caret in that case.
- In practice, a render (`RenderBackplateIfRequired`) creates the manager before the async GotFocus event runs. I couldn't make the gap happen in a test, even when enabling selection and calling `Focus()` in the same UI-thread call. The call just removes the dependency on that ordering.
- `Select()` already makes the same call internally. The manager is only created when selection (or the high-contrast backplate) is on.
- RichTextBlock creates its manager during layout (`EnsureBlockLayout`) and when selection is turned on. A Hyperlink can only get focus after layout, so its branches don't need this.

Compat risk is very low. The change only affects a path that used to crash.

## Tests

New tests in `HyperlinkInTextTests` (`Microsoft.UI.Xaml.Tests.External.Foundation.dll`). Each one focuses a Button, turns on caret browsing, and presses Tab until the Hyperlink has focus (up to 3 times, since the text host can be a tab stop too).

| Test | What it checks |
|---|---|
| `CaretBrowsingTabToHyperlinkInNonSelectableTextBlock` | Hyperlink gets focus. No crash. `SelectionStart` stays null. |
| `CaretBrowsingTabToHyperlinkInNonSelectableRichTextBlock` | Same, for RichTextBlock. |
| `CaretBrowsingTabToHyperlinkInNonSelectableRichTextBlockOverflow` | Same, with the Hyperlink in a RichTextBlockOverflow. Verifies the Hyperlink's visual parent is the overflow, so the RTBO branch runs. |
| `CaretBrowsingTabToHyperlinkInSelectableTextBlock` | Control case. With selection on, the caret moves to the Hyperlink's start. |

The tests live in `HyperlinkInTextTests` because `CaretBrowsingTests` is marked `Ignore` at class level and never runs.

## Not changed

Other caret browsing code (for example `TextSelectionManager` and RichTextBlockOverflow focus/key handling) checks whether a selection manager exists rather than whether selection is enabled. With high contrast active, that manager can exist while selection is off. I didn't find a crash there for this scenario, so I left it alone. It could be a follow-up.
