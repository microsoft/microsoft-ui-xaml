Fix out-of-order member initializers in generated XamlUserType and XamlMember constructors (#11097)

## Bug

Issue #11097: a C++ app turns on warning C5038 (out-of-order member initialization), for example with `/we5038` or `/w15038`. The app then fails to build because of code the Xaml compiler generates in `XamlTypeInfo.Impl.g.cpp`:

```
XamlTypeInfo.Impl.g.cpp(308,15): error C5038: data member '...XamlUserType::_fullName' will be initialized after data member '...XamlUserType::_baseType'
XamlTypeInfo.Impl.g.cpp(575,15): error C5038: data member '...XamlMember::_provider' will be initialized after data member '...XamlMember::_name'
```

C5038 is off by default, so most apps never see this. Apps that use `/Wall`, or that turn it on to catch real init-order bugs in their own code, can't do that with WinUI.

Root cause: the constructor mem-initializer lists in the T4 templates are not in member declaration order.

| Generated class | Members declared in | Old init order | Declaration order |
|---|---|---|---|
| C++/WinRT `XamlUserType` | `CppWinRT_TypeInfoPass1.tt:169-175` | `_provider, _fullName, _baseType` | `_provider, _baseType, ..., _fullName` |
| C++/WinRT `XamlMember` | `CppWinRT_TypeInfoPass1.tt:219-222` | `_provider, _name, _typeName` | `_name, _typeName, _provider` |
| C++/CX `XamlUserType` | `MoComCppTypeInfoPass1.tt:364-378` | six `_isX(false)`, then `_fullName, _provider, _baseType` | `_provider, _baseType, ..., _fullName, ..., six bools` |

The C++/CX `XamlMember` (`MoComCppTypeInfoPass1Impl.tt:701-706`) is already in order, so it isn't changed.

## Fix

Reorder the mem-initializer lists to match declaration order. Nothing else changes.

| File | Change |
|---|---|
| `CppWinRT_TypeInfoPass1Impl.tt:326-328` | `XamlUserType`: `_provider, _baseType, _fullName` |
| `CppWinRT_TypeInfoPass1Impl.tt:595-597` | `XamlMember`: `_name, _typeName, _provider` |
| `MoComCppTypeInfoPass1Impl.tt:434-442` | C++/CX `XamlUserType`: `_provider, _baseType, _fullName`, then the six bools |
| `CppWinRT_TypeInfoPass1Impl.cs`, `MoComCppTypeInfoPass1Impl.cs` | Same edits in the checked-in T4 output |
| 23 `TestMasters\...\XamlTypeInfo.Impl.g.cpp` | Same edits in the codegen master files |
| `Tests\Common\AppPreamble.cpp.props:148`, `RuntimeComponentPreamble.cpp.props:92` | Add `/we5038` so the C++ regression projects catch this |

About the `.cs` files: the build compiles the checked-in T4 output, not the `.tt`. `Core.projitems` sets `TransformOnBuild=$(BuildingInsideVisualStudio)`, so command-line builds never regenerate it. So the `.tt` and `.cs` are edited together. In the C++/WinRT `.cs`, the generated code is one long string literal. I re-split it so only the init lines move.

## Why this fixes the issue

- C5038 fires when the order of a constructor's mem-initializer list differs from the order the members are declared in. The two errors in the issue point at exactly the `XamlUserType` and `XamlMember` constructors.
- After the fix, each list names members in the same relative order as their declarations (see the table above). So C5038 has nothing to report.
- Red/green with the `SimpleCppWinRT` regression project and `/we5038`:
  - Before: the build fails with the two errors above, at the same lines (308,15) and (575,15) the issue reports.
  - After: 0 errors.
- The full `XamlCompilerTests.sln` (all C++/WinRT regression projects) also builds with `/we5038` on and 0 errors. So no other generated class has this problem in those projects.

## Why it's safe

- **Runtime behavior is identical.** In C++, members are always initialized in declaration order, no matter how the mem-initializer list is written ([class.base.init]). The declarations don't change, so the real init order, object layout, and destruction order don't change either.
- **No initializer reads another member.** Each one copies a constructor parameter (`provider`, `fullName`, `baseType`, `name`, `typeName`) or a constant `false`. So even the "written" order never mattered.
- **No runtime change.** The fix touches only text the Xaml compiler emits into the app's own source. `Microsoft.UI.Xaml.dll` and other runtime binaries don't change.
- **Compat with apps built with the old Xaml compiler:**
  - An app that isn't rebuilt keeps its old generated code, which works the same as before.
  - An app rebuilt with the new compiler gets the reordered lists. Its behavior is the same, and C5038 is now clean.
  - No public API, ABI, or metadata changes.
- **Who sees a difference:** only apps that compile with C5038 on. They go from a warning or error to a clean build.
- **`/we5038` in the test preambles** applies to the regression projects only, not to shipped targets. The full test sln builds with it.

## Tests

- Regression test: `/we5038` in the two C++ regression preambles. If a template ever emits out-of-order inits again, the C++ regression projects fail to build.
- `CodegenTests` (`Codegen_DiffCodegenFiles_*`) compare generated output to the 23 updated masters. All passed. The `Simple` master is byte-identical to a fresh build's generated file.

The 4 failures are `WMC0155_ListViewCollectionCreatedWithSuccinctSyntax`, `WMC0155_CheckSyntacticallyValidInput`, `WMC0155_CheckSyntacticallyInvalidInput` and `WMC0155_ListViewDuplicateError`. They fail with "Unexpected Error WMC0050: Cannot assign ... into the read only property 'Items'". They fail the same way with the origin/main compiler, so they're pre-existing and not from this change. They test XAML validation, which doesn't use the C++ templates.

The skip count (4 vs 5) varies between runs. `CanCallXbfGen` is skipped when the test assembly is built with `Platform=x64` (`XamlCompilerUnitTests.csproj:24-26` defines `DO_NOT_USE_GENXBF`). That depends on how the test DLL was built, not on this change.

## Not covered

- **C++/CX has no compile test.** There's no C++/CX regression project, so nothing compiles the C++/CX `XamlUserType` with `/we5038`. Its new order is checked by reading `MoComCppTypeInfoPass1.tt:364-378`. The six bools have `= false` defaults there, so their mem-initializers are redundant. I kept them to keep the diff small.
- Other generated files (`XamlBindings`, `XamlMetaDataProvider`, etc.) built clean with `/we5038` in the C++/WinRT regression projects. That covers the feature mix those projects use, not every possible template branch. Reviewers also read every other mem-initializer list in the C++/WinRT and C++/CX templates, including branches no regression project builds (for example `XamlConsolidatedType` at `MoComCppTypeInfoPass1Impl.tt:783-785`). All of them have one entry or are already in order.
- `dxaml\test\native\external\Automation\xamluiabridge\XamlTypeInfo.Impl.g.cpp` is an old checked-in C++/CX output used by a runtime test. It isn't regenerated from these templates and still has the old `XamlUserType` order (lines 194-201). It's harmless, since `dxaml\common.props:84` turns C5038 off. I left it alone.
