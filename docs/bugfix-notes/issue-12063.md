Fix crash when a backdrop XamlCompositionBrushBase is used with rounded corners, an Ellipse, or a BorderBrush (#12063)

## Bug

Issue #12063: an app has a `XamlCompositionBrushBase` (XCBB) whose `CompositionBrush` is a `CompositionBackdropBrush`. It works as the `Background` of a plain rectangle. But the app fail-fasts when the same brush is used in any of these ways:

| Usage | Xaml path |
|---|---|
| `Border.Background` with `CornerRadius` | `WUCBrushManager::GetMaskBrush` |
| `Border.BorderBrush` with `CornerRadius` | `WUCBrushManager::GetMaskBrush` |
| `Border.BorderBrush` with square corners | `WUCBrushManager::GetNineGridBrush` |
| `Ellipse.Fill` (and other shapes that use a mask) | `WUCBrushManager::GetMaskBrush` |

In these cases Xaml doesn't paint the app's brush directly. It wraps it in a `CompositionMaskBrush` or a `CompositionNineGridBrush` and passes the app's brush as `Source`.

DComp rejects a `CompositionBackdropBrush` as `Source` of those brushes. `put_Source` returns `E_INVALIDARG`, and the `IFCFAILFAST` around it takes the app down (0xC000027B).

DComp does accept an effect brush that has a backdrop as one of its inputs. That's why `AcrylicBrush` (also an XCBB) works with rounded corners.

## Fix

New helper `WUCBrushManager::WrapBackdropBrushForSource`, called from the XCBB branches of `GetMaskBrush` and `GetNineGridBrush`:

- If the brush is not a `CompositionBackdropBrush`, it's returned unchanged. All other brushes behave as before.
- If it is a backdrop brush, the helper wraps it in a `CompositionEffectBrush` that passes the backdrop through unchanged. DComp accepts that effect brush as `Source`.
- The effect is a `CompositeEffect` (SOURCE_OVER) that draws a transparent `ColorSourceEffect` over the backdrop. Drawing transparent pixels over the backdrop doesn't change it.
- The effect factory is created once and cached. `ReleaseDCompResources` resets it with the rest of the compositor state.
- Each wrapper gets a fixed `Comment` (`Microsoft.UI.Xaml.BackdropPassThrough`). On later frames, if the existing `Source` has that comment, it's our wrapper, so it's reused. If the app handed Xaml a different backdrop instance, the wrapper's source parameter is updated in place. So we don't create a new effect brush every frame.
- Effect brushes without the comment (for example an `AcrylicBrush` the element used before) are never probed or changed. Setting the comment is best effort. If it fails, we just create a new wrapper each frame.
- Only brushes that implement `ICompositionBackdropBrush` are wrapped. That includes `CompositionBackdropBrush` and the host backdrop brush.

Effects I tried:

| Effect | Result |
|---|---|
| None (raw backdrop as `Source`) | `put_Source` fails with `E_INVALIDARG` |
| `Transform2DEffect` (identity) | `SetSourceParameter(backdrop)` fails with `E_INVALIDARG`, with both mock and real DComp |
| `CompositeEffect` + transparent `ColorSourceEffect` | Works |

These are the effect classes already in `dxaml\xcp\core\hw\Effects.h`, so no new effect class was needed. The brushes component now includes `hw/effects.h`, so its vcxproj gets `$(XcpPath)\core` as an include dir. `FocusRect` does the same.

Compat risk is low. The new code only runs for a backdrop XCBB in the mask or nine-grid paths, and those paths used to crash.

## Tests

New tests in `BorderTests` (`Microsoft.UI.Xaml.Tests.External.Foundation.dll`). They use a small `BackdropXcbb` class that sets `CompositionBrush` to `Compositor.CreateBackdropBrush()`.

Each test:

1. Puts the element in the window with the backdrop brush and waits for a frame.
2. Resizes the element (and changes `CornerRadius`, or the text) so the mask or nine grid is updated. This covers the wrapper-reuse path.
3. Has the XCBB hand Xaml a new backdrop brush instance. This covers updating the existing wrapper in place.
4. Switches to a `SolidColorBrush` and back to the backdrop brush.

| Test | Scenario |
|---|---|
| `BackdropXcbbRoundedBackground` | `Border.Background`, `CornerRadius` 20 |
| `BackdropXcbbRoundedBorderBrush` | `Border.BorderBrush`, `CornerRadius` 20, thickness 8 |
| `BackdropXcbbSquareBorderBrush` | `Border.BorderBrush`, square corners, thickness 8 (nine grid) |
| `BackdropXcbbEllipseFill` | `Ellipse.Fill` |
| `BackdropXcbbTextBlockForeground` | `TextBlock.Foreground` (text uses a mask too) |

The tests check that the app doesn't crash. They don't compare pixels. Mock DComp doesn't render backdrops, so a pixel check wouldn't say much.

## Validation (local Hyper-V VM, amd64chk)

| Test | Before fix | After fix |
|---|---|---|
| `BackdropXcbbRoundedBackground` | Failed (host crash, 0xC000027B) | Passed |
| `BackdropXcbbRoundedBorderBrush` | Failed (host crash, 0xC000027B) | Passed |
| `BackdropXcbbSquareBorderBrush` | Failed (host crash, 0xC000027B) | Passed |
| `BackdropXcbbEllipseFill` | Failed (host crash, 0xC000027B) | Passed |
| `BackdropXcbbTextBlockForeground` | Failed (host crash, 0xC000027B) | Passed |

- Full `BorderTests` class after the fix: 19/19 passed.
- I also ran the new tests with mock DComp turned off (real DComp). The `Transform2DEffect` attempt failed the same way there, so the `E_INVALIDARG` comes from real DComp, not just the mock. The final fix passed 5/5 with real DComp. For that run I also added a temporary check that the wrapper's `Comment` reads back correctly, so the reuse path really runs.
- `BrushTests` and `PopupIntegrationTests::HostBackdropBrush*` also use XCBBs, but they're marked `Ignore` and don't run.

## Not changed

- I didn't check the rendered output on a real desktop. The backdrop should look the same as it does without rounding, clipped to the mask or nine grid. A quick visual check in an app would be good before shipping.
- Only backdrop brushes are wrapped. Other XCBB brushes go through unchanged, as before.
- The WUC shapes path (`CShape::PopulateCompositionSpriteShape`) also sets an XCBB brush directly. It's only used when the `WUCShapes` feature is on, and that feature is off. So it isn't changed here.
