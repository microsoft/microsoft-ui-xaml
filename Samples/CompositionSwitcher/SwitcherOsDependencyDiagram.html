Dispatcher and CoreMessaging dependency

A WinRT compositor needs scheduling for commits and deferred callbacks, plus a session that receives DwmCore callbacks. The current switcher path bridges a lifted scheduling session to a system callback session. A system DispatcherQueue can use one system session for both roles.

Current switcher: lifted scheduling session

The compositor schedules through CoreMessagingXP, but DwmCore must communicate through system CoreMessaging. dcomp therefore creates and manually drains a second session.

Separate-thread comparison

WinUI already has a separate composition/render thread. The proposed design does not merely replace the implementation on that thread: it changes what the thread owns, how it pumps work, and the contract between XAML and composition.

Current: lifted XAML composition/render thread

XAML owns a custom high-priority MTA scheduler thread. It advances the frame clock, wakes the UI thread for ticks, and consumes render commands. It is not a public DispatcherQueue-owned compositor apartment.

Proposed: system compositor on a separate owner thread

The separate thread owns a system DispatcherQueue, its CoreMessaging session, the public system Compositor, and the visual tree. XAML keeps its lifted DispatcherQueue on the UI thread.

Main migration cost Baseline behavior. Audit and adapt every direct or synchronous XAML-to-composition operation.
Key conclusion: both designs use a separate thread, but the current thread is a XAML render scheduler while the proposed thread is the owner of the system WinRT compositor object graph. Reusing the physical thread still requires replacing or extending its custom loop with a system DispatcherQueue and defining an explicit marshalling contract.
